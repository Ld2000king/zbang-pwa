# זבאנג רויאל (Zabang Royale)

A Hebrew word game, built as a static PWA and wrapped for native with Capacitor.

There is no bundler — the web app is the set of plain `.js` / `.css` files at the
repo root, loaded directly by `index.html`. `scripts/copy-web.mjs` copies just the
real web assets into `www/`, which is what Capacitor ships as its `webDir`.

| | |
|---|---|
| Bundle ID | `com.zabang.royale` |
| Version / build | `1.0` / `1` (Xcode: `MARKETING_VERSION` / `CURRENT_PROJECT_VERSION`) |
| Min iOS | 13.0 |
| Backend | Firebase Realtime Database + Anonymous Auth |

---

## Running the web app

Any static server from the repo root works — but use a server, not `file://`,
or the service worker won't register:

```bash
npx serve .          # or: python3 -m http.server 8000
```

## Building the native bundle

```bash
npm install
npm run build:web    # rebuilds www/ from the repo root
```

`www/` is generated and gitignored; it is rebuilt on every `npm run sync`.

## iOS: wrapping and shipping

**`ios/` is committed.** The Xcode project, the app icon, the splash set and a
configured `Info.plist` are all in the repo, so nothing needs to be scaffolded.

What is *not* in the repo, and cannot be, is anything that requires macOS:

- **CocoaPods has never run.** There is no `ios/App/Pods/` and no `Podfile.lock`.
  This matters more than it looks: Capacitor's own iOS runtime — the native
  bridge that actually hosts the web app — is delivered as a pod. Until
  `pod install` runs, the project contains the shell but not the engine.
- `ios/App/App.xcworkspace` is therefore incomplete: its `contents.xcworkspacedata`
  (the file that links `App.xcodeproj` to `Pods.xcodeproj`) is generated by
  `pod install`. This is normal, not damage.
- The project has never been compiled. No `.app`, no `.ipa`, and it has never
  been run on a simulator or a device.
- No signing team is set.

### On the Mac

Requires Xcode (with the iOS platform installed) and CocoaPods (`brew install cocoapods`).

```bash
npm install
npm run sync         # build:web -> www/, copies it into ios/, runs pod install
npm run open:ios     # opens App.xcworkspace in Xcode
```

Use `npm run sync`, not a bare `npx cap sync ios`. `www/` is gitignored, so on a
fresh clone it does not exist yet, and `cap` on its own does not build it — it
fails with *"Could not find the web assets directory: ./www"*. The npm script
chains `build:web` first.

Then in Xcode:

1. Select the **App** target → **Signing & Capabilities** → set your **Team**.
   Xcode will provision `com.zabang.royale` automatically.
2. **Run** on a simulator or device. *This is the first time the app has ever
   been built* — treat whatever happens here as the real result, not a formality.
3. Bump **Version** / **Build** for each App Store upload.
4. **Product → Archive** → **Distribute App** → App Store Connect.

Re-run `npm run sync` after any change to the web files, otherwise Xcode keeps
shipping the previously copied `www/`.

### Check these by hand on the first run

Everything below was verified in a desktop browser against the built `www/`
bundle, which is not the same as a `WKWebView` on a device:

- **The privacy and terms links.** In the HTML they carry `target="_blank"`,
  which is right on the web but opens a chrome-less window with no back button
  inside a `WKWebView`. `keepLocalPagesInShell()` in `index.html` strips the
  attribute at runtime — but only for local pages, and only when
  `isNativeShell()` is true. Open both from the menu and confirm you can get
  back to the game. App Review opens the privacy policy, so it has to be
  reachable *and* escapable.
- **Audio.** `background-music.mp3` autoplay is restricted differently in a
  webview than in Safari.
- **Safe areas.** The layout uses `viewport-fit=cover`; check the notch and the
  home indicator against the fixed bottom nav.
- **Firebase connectivity.** Multiplayer and the leaderboard need the network;
  the app is built to fall back to single-player when Firebase is unreachable,
  so a silent fallback can look like success.

### iPad

`TARGETED_DEVICE_FAMILY` is `"1,2"`, so the app claims iPhone **and** iPad
support, and Apple will review it on an iPad. The layout is a portrait
phone design. Either check that it holds up on an iPad, or set the target to
iPhone-only (`"1"`) before submitting.

## Firebase

`firebase-config.js` holds the client config. The `apiKey` there is a public
client identifier, not a secret — access is enforced by the Security Rules in
`database.rules.json`.

**Two steps are still outstanding, and both can be done from any machine:**

1. **Replace every `PASTE_ADMIN_UID_HERE`** in `database.rules.json` with the
   real UID of the admin account (Firebase Console → Authentication → Users).
   Until then the admin features — the word-approval queue, word-bank edits and
   the leaderboard rename — cannot work, because no UID satisfies the rule.
2. **Publish the rules.** Editing the file in git changes nothing in
   production — Firebase Console → Realtime Database → Rules → paste → Publish.
   (`firebase deploy --only database` needs a `firebase.json` pointing at
   `database.rules.json`; the repo has no `firebase.json`, so the Console is
   the path today. Note the file has `//` comments, which the Console accepts.)

Step 2 is what activates the leaderboard access-control fix. Without it, any
signed-in client — including the anonymous session every visitor gets — can
still overwrite any other player's leaderboard row.

## Regenerating icons and splash screens

`Logo.png.jpeg` at the repo root is the single source of truth.

```bash
npm run generate:icons          # -> assets/, store/, and the PWA icons at root
npm run generate:native-assets  # -> the iOS/Android Assets.xcassets sets
```

PNGs are written at `compressionLevel: 9, effort: 10` (see `PNG_OPTS` in
`scripts/generate-icons.mjs`). That is lossless — identical pixels, a harder
DEFLATE search — but these are large flat-colour canvases, so it is worth
roughly 5x on disk and in the shipped binary.

The App Store icon (`store/app-store-icon-1024.png`) must stay 1024×1024 **with
no alpha channel**; Apple rejects icons with transparency. `squareOpaque()`
handles that, but re-verify if you change the pipeline.

## Vendored dependencies

`vendor/` is committed on purpose — nothing third-party is fetched at runtime:

- `vendor/firebase/` — the Firebase compat SDK 10.13.2, the same UMD bundles
  Google serves from `gstatic.com`, taken from the npm package. To upgrade:
  `npm pack firebase@<version>` and copy the three `firebase-*-compat.js` files.
- `vendor/fonts/` — Rubik and Poppins from `@fontsource`, only the weights the
  app actually uses. The `@font-face` rules are at the top of `style.css` and
  carry Google's own `unicode-range` split, so the Hebrew and Latin subsets load
  separately.

Both were previously loaded from a CDN. In a native shell that meant a cold
start waited on the network before Firebase came up, and the game rendered in a
fallback system font — including the Hebrew display type the whole design rests
on.

`sw.js` is a web-only concern — `registerSW()` skips it when `isNativeShell()`
is true, since the native app already has every file inside the binary. Anything
added to `PRECACHE` still needs the `VERSION` constant bumped in the same
commit, or existing web installs keep serving the old cache.
